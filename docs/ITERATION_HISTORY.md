# 项目迭代与设计决策

本项目围绕一个目标推进：让本地模型提出的工单操作经过校验、实际执行并形成可核对的证据答复。本页整理影响最终配置的关键阶段和设计依据，具体实验产物通过链接定位；全部历史试验和运行日志没有随当前仓库公开。

## 先理解四套版本号

| 版本对象 | 本项目采用的版本 | 说明 |
|---|---|---|
| 基座模型 | Qwen2.5-7B-Instruct | 上游模型版本 |
| 微调适配器 | retention v1.2 LoRA | 项目内的微调训练版本；retention 指兼顾已有工具能力保持 |
| 执行层 | trusted completion v1.7 | 项目内的守卫、恢复和证据完成版本 |
| 验收数据 | 独立 v6 | 项目内的正式评测集版本 |

最终 v6 的两个对照臂都使用同一 retention v1.2 LoRA，分别接入 v1.6 和 v1.7 执行层。因此 154/160 到 160/160 的差异归属于这次执行层对照，不能当作新一轮 LoRA 训练收益。

## 阶段一：建立本地模型与工单数据链路

基于已有工具调用 LoRA 继续进行工单领域 SFT，构建包含权限、澄清、事实忠实、知识链等主题的中英多轮数据。最终采用的 retention v1.2 配方为 1800 条记录、900 中英配对、5202 个 assistant 回合，LoRA rank 8、alpha 16、dropout 0.05，训练 1 epoch、225 个优化步。

训练 loss 和张量变化能说明训练运行及参数更新情况，仍需执行评测判断工单任务是否完成。后续开发没有将所有尝试过的修复适配器都纳入最终配置。

证据：[训练配置](../configs/ticket_policy_retention_train_v1_2.yaml)、[训练验证记录](../results/training/train/verification.json)、[数据清单](../data/ticket_policy_retention_train_release_v1_1/manifest.json)。完整重训所需资源和历史前置产物仍有缺口，见[训练与资源交付](TRAINING_AND_ASSETS.md)。

### 微调版本与实验分支

微调适配器改变模型参数，工具执行层改变普通程序逻辑；两者有独立版本。下面按模型侧的主要链路区分：

| 模型侧版本 | 改动与用途 | 最终是否采用 |
|---|---|---|
| Hermes 工具调用 LoRA（r8） | 提供通用工具调用训练起点 | 属于初始化链路 |
| ticket-sft-v3（Hermes r8 工单续训） | 从 Hermes LoRA 继续学习工单任务 | 是 retention 训练的直接初始化来源 |
| retention v1.1 | 建立中英工单策略与能力保持训练配方 | 当前系统未加载此版本 |
| retention v1.2 | 保持主要训练配方，建立独立训练产物与更明确的 GPU/环境/结果核验 | 是最终冻结适配器 |
| repair-lr2p5e-8 / repair-lr5e-8 | 从 retention v1.2 出发，对比两种低学习率修复 | 是旁支，最终未采用 |
| answer-contract-lr1e-7 | 从 retention v1.2 出发，修复回答格式、完整性与证据表达 | 是旁支，最终未采用 |

核对原配置可见，retention v1.1 与 v1.2 的主要训练超参数、初始化适配器和训练数据保持一致，配置中的输出目录不同；v1.2 的执行代码另外绑定物理 GPU2、检查 UUID/环境并独立核验训练结果。这里将其作为训练工程差异记录，不声称 v1.2 因某个新算法而天然优于 v1.1。

学习率修复和回答契约修复属于相同父适配器上的候选实验，而非执行层 v1.3-v1.7 的前后继权重。最终系统继续使用 retention v1.2，以便对运行时变化作同权重比较。

本页对旁支作历史说明，公开快照没有完整分发其权重和所有评测轨迹，因此不据此给出旁支模型质量排名。训练脚本、交付执行包或预检编号的变化，也不自动代表模型能力版本变化。

## 阶段二：先把失败定位清楚

面对低完成率，按以下层次拆分，而不是只看一个总分：

| 检查层 | 要回答的问题 |
|---|---|
| 模型输出 | 是否能解析为合法工具调用？字段和类型是否满足 schema？ |
| 工具行为 | 目标工单、用户身份、搜索条件及操作范围是否符合请求？ |
| 最终状态 | 需要的动作是否真的完成？是否有未请求的状态变化？ |
| 回答证据 | 最终陈述是否来自实际工具结果，字段是否完整？ |
| 数据与评分 | 可信参数是否对模型可见？漏字段是否被错误归类？ |
| 终止 | 是安全停止、预算耗尽、重复循环，还是成功释放证据？ |

这一区分决定修复位置：任务契约缺失应修数据；评分问题应单列修正；真实工具失败应修模型或执行链路。正式冻结成绩不被事后语义复核覆盖。

## 阶段三：从“拦截错误”走到“完成可信目标”

守卫先建立调用边界，再逐步补齐恢复能力。较早版本是后续版本的实际依赖，当前仓库保留其实现和来源绑定。

| 执行层 | 触发问题 | 关键改进 | 源码 |
|---|---|---|---|
| controller v1.1 | 需要基础调用、状态和答复约束 | 建立基础执行检查 | [基础控制器](../extensions/ticket_runtime_controller_v1_1/core.py) |
| contract guard v1 | 读取和状态更新中的目标偏离、额外变更、答复证据问题 | 可信目标绑定和证据释放，初始覆盖两个工具 | [初始契约守卫](../extensions/ticket_runtime_contract_guard_v1/core.py) |
| contract guard v1.1 | 错误目标、身份、条件或不可靠的最终陈述 | 绑定可信契约、检查调用范围、基于后端证据渲染 | [守卫](../extensions/ticket_runtime_contract_guard_v1_1/core.py) |
| transaction recovery v1.2 | 事务被拒后未能继续完成任务 | 保持拒绝事务无提交，进入受控恢复 | [事务恢复](../extensions/ticket_runtime_transaction_recovery_v1_2/core.py) |
| blocked action recovery v1.3 | 错误负责人、身份或扩大搜索条件被拦截后卡住 | 原调用先拦截，再恢复可信目标 | [拦截后恢复](../extensions/ticket_runtime_blocked_action_recovery_v1_3/core.py) |
| general recovery v1.4 | 错误 KB 查询、分配重读等故障 | 通用查询与重读恢复，检查真实激活事件 | [通用恢复](../extensions/ticket_runtime_blocked_action_recovery_v1_4/core.py) |
| evidence completion v1.5 | 多余参数和知识正文证据不完整 | 受限 schema 投影、读取已返回文章的正文 | [证据补全](../extensions/ticket_runtime_evidence_completion_v1_5/core.py) |
| exact create recovery v1.6 | 创建的标题、描述、优先级或请求人偏离契约 | 按请求中完整且可见的冻结载荷精确创建 | [精确创建](../extensions/ticket_runtime_exact_create_recovery_v1_6/core.py) |
| trusted completion v1.7 | 搜索标识符大小写变化、错误工单重读循环、完成后继续生成 | 精确搜索、可信目标重读、已有证据直接释放 | [可信完成](../extensions/ticket_runtime_trusted_completion_v1_7/core.py) |

这些恢复只使用可信契约中完整且可见的值。缺失必需值时关闭恢复，不从错误模型提议中复制参数，也不猜测新的执行目标。

## 阶段四：验证恢复机制确实生效

仅有较高完成率，不能证明新增恢复代码被触发。因此开发验证同时检查：

- **故障激活**：预设故障是否真的到达对应守卫与恢复分支。
- **执行前拦截**：原错误调用是否在进入后端前被阻止。
- **精确调用**：恢复参数是否逐字段等于可信契约，标识符大小写是否保持。
- **任务完成**：后端状态和证据是否满足原请求。
- **正常路径保护**：无故障任务是否发生回归。
- **安全边界**：拒绝事务是否无提交，是否存在越界或额外变更。

开发中的保护题可采用全通过门槛检测工程回归；正式验收采用执行前冻结的总体、工具和分层门槛，并不要求所有系统在所有任务上永远满分。

早期开发暴露过隐藏可信参数、恢复未实际激活等评测设计问题，后续通过显式可见契约和事件门槛消除混淆。这些修正需要保留原结果和新数据边界，不能把旧成绩直接改成成功。

## 阶段五：冻结独立 v6，完成同权重对照

开发修复完成后，冻结新 seed、新实体、新表达和新组合的 v6：160 题、8 工具，每工具正常/故障各 10 题；同一模型和适配器执行两臂，共 320 条轨迹。GPU worker 只读任务，退出后 CPU scorer 才读取 oracle。

| 指标 | v1.6 执行层 | v1.7 执行层 |
|---|---:|---:|
| 完成数 | 154/160 | 160/160 |
| 工单搜索 | 16/20 | 20/20 |
| 状态更新 | 18/20 | 20/20 |
| 其余 6 工具 | 各 20/20 | 各 20/20 |
| 无效模型输出次数 | 1 | 0 |
| 特殊前缀无额外模型回合释放 | 0/30 | 30/30 |
| 记录中的硬安全违规 | 0 | 0 |

候选通过执行前冻结的全部门槛：总体至少 152/160、每工具至少 18/20、每工具正常/故障各至少 9/10，同时满足特殊恢复调用、无效输出为 0 和安全违规为 0 的要求。

既有 AI 辅助全量语义复核确认：对照有 4 条标识符大小写相关搜索循环、2 条错误目标重读循环失败，候选在这些任务上完成。这里没有宣称人工逐条审核。

证据：[正式准入规则](../data/ticket_runtime_prospective_holdout_v6/admission.json)、[正式结果](../results/v6/comparison.json)、[AI 辅助复核摘要](../reports/ticket-runtime-prospective-blind-v6-semantic-review-v1/summary.json)、[结果解释](EVALUATION.md)。

不同开发集或正式集的分数不作直接纵向比较。已经暴露的开发集及 v3-v6 均不能再次作为后续版本的独立验收；公开 v6 可用于回归检查，新的效果主张需要新的独立数据。

## 阶段六：从评测脚本交付到交互演示

完成离线集成发布候选后，接入真实本地 Qwen 推理和会话隔离的模拟后端。界面展示用户确认参数、模型输出、工具调用、守卫决定、工单前后状态和证据答复。

- 既有本地模型演示日志覆盖 8 个工具、10 次完成请求、12 个模型回合，无效输出 0；公开的是去除原始会话内容后的汇总。
- 20 项 CPU 演示测试覆盖会话隔离、幂等、连续创建 ID、错误目标恢复、HTTP 鉴权和停机控制；另有 2 项公开入口路径迁移测试。
- GitHub Actions 运行 CPU 测试和只读评分复算。源码、轨迹和文档通过发布哈希清单登记。

证据：[演示汇总](../results/interactive-session-summary.json)、[演示实现与测试](../extensions/ticket_interactive_demo_v1)、[CPU CI](../.github/workflows/cpu.yml)、[项目技术报告 PDF](qwen-ticket-agent-project-report.pdf)。

## 当前边界与后续工作

160/160 是自建合成 v6 上的系统成绩，覆盖了预设故障和可信契约场景。部分故障前缀由守卫完成，不能把它解释成 160 条全部由模型自主规划成功，也不能推导真实业务必然正确。

当前仍需用户选择操作并确认结构化目标；模拟状态保存在内存，安全停机不撤销已提交变更。完整训练资产还未全部公开，真实后端连接器、任意自然语言意图提取、持久化和并发场景尚未形成验收结论。

后续优先补齐资源来源与交付，再分别评测意图提取、持久化和非真实后端接口适配；保留现有守卫边界，并为新增能力准备新的独立验收。
